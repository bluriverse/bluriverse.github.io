Bluriverse Hotels: securing a hotel front-desk workstation

A hotel's most exposed computer, shared and sitting next to the payment terminal, hardened, measured and proven end to end.

A fictional franchised hotel, "Hôtel Bluriverse Versailles", whose front-desk workstation is shared by the team and installed next to the payment terminal. A poorly protected workstation can open the door to the card payment environment: the goal was to align it with the security requirements of such environments, through a repeatable approach applied from headquarters and verified on the workstation itself.

Personal lab environment and fictional scenario: no real data, no real organisation described.

01What is at stake

The front-desk workstation is a hotel's most exposed computer: shared by several people, used in front of guests, sitting next to the payment terminal. Once compromised, it can become an entry point into the card payment environment, with financial and reputational consequences for the hotel and the brand alike.

In a network of franchised hotels the challenge is twofold: enforcing the same security level everywhere from headquarters, and being able to prove that this level is actually reached on every workstation.

02Lab architecture

  • bluriverse.corp domain with domain controller DC01, on an isolated internal network.
  • RECEP01 workstation running Windows 11 Enterprise, joined to the domain through a delegated join account, and placed in a dedicated OU "Tier 2 › Hotel Versailles › Front desk workstations".
  • GVM01 VM running Ubuntu, used as a network scanner (nmap and NSE scripts).
  • No licences: cloud components (Conditional Access, PIM, Intune) are described as a target configuration, without any trial enabled.

03Measures implemented

Named accounts
One personal account per receptionist, in a dedicated group, allowed to sign in only on the front-desk workstation: every action becomes attributable.
GPO hardening
C_T2_HARDENING_RECEPTION GPO: lock after 10 minutes, last user hidden, cached credentials limited, LLMNR disabled, SMB signing required, USB storage blocked, 14 attack surface reduction rules.
Encryption
BitLocker with XTS-AES 256 and a TPM protector, with the recovery password mandatorily backed up to Active Directory.
Tiering
Sign-in denied to domain and enterprise administrators on the workstation, and Domain Admins removed from the local Administrators group.
Traceability
Enlarged security log and PowerShell script block logging, to reconstruct a session after an incident.
Workstation hygiene
NetBIOS disabled, automatic sign-in removed along with its stored password, all applied through a startup script.

04Measure, then prove

A PowerShell script assesses the workstation against 27 controls grouped by theme (access, session, encryption, protection, network, credentials, devices, logging) and produces a timestamped JSON report. Before: 48% (13/27). Final: 96% (26/27).

The only remaining gap is local administrator password rotation (LAPS): in this lab it would require an irreversible Active Directory schema extension. This is a deliberate, documented choice; the target configuration covers it through backup to Entra ID, without touching the schema.

05Three "false compliances"

An "encrypted" disk that protected nothing
The disk showed as fully encrypted, but without any protector: the key was in the clear. The workstation was decrypted, then re-encrypted with XTS-AES 256, a TPM and the key backed up to the directory.
A validated GPO that never arrived
The GPO looked correct on the server side, yet no value was applied on the workstation: two client-side extension identifiers were wrong. Diagnosed from the workstation, fixed, then verified by a control script.
Encryption blocked at boot
BitLocker activation failed because installation media was still mounted on the workstation. The script was made resilient to this case for large-scale deployment.

Lesson: "compliant" on a dashboard is not enough. It has to be proven where the risk actually lives, which is what automated checks run on the workstation make possible.

06Network scan and remediation plan

  • nmap scan with NSE scripts from the Ubuntu VM, across the whole lab network.
  • Compliant: SMBv1 absent, SMB signing required, the front-desk workstation exposes a single port.
  • Gaps on the domain controller: unsigned simple LDAP bind accepted, no LDAPS, NetBIOS active, WinRM open.
  • Prioritised remediation plan for a team of three engineers over four weeks: LDAP signing (after an audit phase) and NetBIOS first, then LDAPS with channel binding, WinRM restriction and authenticated scanning.

07Microsoft target configuration

  • Eight Conditional Access policies, starting in report-only mode, with two break-glass accounts.
  • Role-based PIM, aligned with the administration tiers: no standing administrators.
  • Intune equivalents of the lab GPOs, and LAPS backed up to Entra ID.
  • Microsoft 365: external sharing, sensitivity labels and DLP for card data.
  • Four-phase rollout (pilot in one hotel, then waves) with measurable exit criteria.

08Deliverables

  • Illustrated logbook of the work, mistakes included.
  • Scope note: network zones, assumptions to validate and a responsibility matrix between headquarters, franchised hotel and service providers.
  • One-page executive summary, jargon-free, with the decisions required.
  • Vulnerability remediation plan, prioritised and sized in effort.
